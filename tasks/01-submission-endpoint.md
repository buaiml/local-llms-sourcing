# Task 01: Website and result submission endpoint

## Goal

Stand up a website with a remote endpoint the CLI can call to submit benchmark results. The CLI generates a result file for each run and saves it locally. When the user chooses to submit, the CLI sends that file to our backend, and the backend stores it in object storage.

## Scope

1. Define the result file format (the file the CLI generates).
2. Build the backend endpoint that accepts a result file and stores it.
3. Stand up the website that hosts the endpoint. A minimal landing page is enough for now.

Out of scope: the CLI runner itself, aggregation, and recommendations. This task only covers the file format and the submit/store path.

## Result file

One JSON file per run. Draft fields (finalize while implementing):

- `schema_version`: integer, so the format can evolve
- `run_id`: unique ID generated by the CLI
- `timestamp`: UTC, ISO 8601
- `hardware`
  - GPU(s): name, VRAM, driver version
  - CPU: model, core count
  - System RAM
  - OS
- `model`: name, source/distributor, parameter count
- `quantization`: e.g. `Q4_K_M`, `fp16`
- `inference_engine`: name and version
- `speculative_decoding`: enabled flag, plus draft model if enabled
- `outcome`: `success`, `failed`, or `incompatible`. Failed and incompatible runs are valid submissions, because knowing what doesn't work is useful.
- `failure`: present when the outcome isn't `success`. Reason, error message, and relevant logs.
- `task`: see below
- `metrics`: see below. Empty or partial for failed and incompatible runs.

### Task

A run is one of two kinds:

- **Freeform use**: the user is just using the model for something, such as chatting.
  - `kind`: `"freeform"`
  - `description`: what the user says they are doing, e.g. "chatting"
- **Benchmark**: the user ran a benchmark.
  - `kind`: `"benchmark"`
  - `benchmark`: benchmark name and version
  - `parts_run`: which parts of the benchmark were run (subsets, categories, or sample counts), so partial runs are comparable

### Metrics

- Speed: tokens/sec, time to first token
- Memory: peak VRAM and RAM
- Token lengths: input token count and output token count per response (summarized across the run, e.g. mean, median, min, max, plus the per-response values). We care about length because it hints at how verbose or semantically dense different models are.
- Benchmark score, when the task is a benchmark

## Endpoint

- `POST /api/submissions` with the result file as the JSON body.
- Anonymous. No API key and no auth.
- Validate against the schema. Reject malformed files with a `400` and a message saying what failed.
- Reject unsupported `schema_version` values.
- Accept files with a non-`success` outcome. Don't require metrics for them.
- Cap request size.
- On success, upload the file to object storage and return `201` with the stored submission ID.
- Re-sent files with the same `run_id` are idempotent (no duplicate record).

## Storage

- Use **Neon object storage**. Hosting is otherwise up to whoever builds this, but this is the recommended option because it is easy to use with Claude Code.
- The storage is entirely server-side. Users never see or hold storage credentials. The CLI talks only to our backend, and the backend uploads the file to the bucket.
- Key objects by `run_id`, so a repeat submission overwrites the same object instead of creating a duplicate.

## Privacy

- The CLI only generates a result file. What gets submitted is that file and nothing else.
- When the user submits, the CLI points at the file and says plainly that this file is what is being uploaded.
- Submission is opt-in; the CLI never sends without user action.
- Submitters stay fully anonymous.

## Acceptance criteria

- [ ] Result file schema documented and versioned, covering both freeform and benchmark tasks
- [ ] `POST /api/submissions` accepts a valid file, stores it in Neon object storage, and returns `201`
- [ ] Invalid files return `400` with a useful error
- [ ] Duplicate `run_id` does not create a second object
- [ ] No storage credentials are exposed to the CLI or the user
- [ ] Website deployed at a public URL
- [ ] Example result file and `curl` command in the docs

## Non-goals for now

- Spam and fake-result protection
- Submitter accounts, API keys, or display names
